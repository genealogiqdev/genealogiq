# Gen2026 manual settlement acceptance — 2026-10-07

## Scope and source

The requested coupon is for old stock and sales already paid through another gateway, including InfinitePay. The user explicitly chose application **by staff in BMS after confirmation**, for a finite purchased period/package without automatic renewal. This implementation does not charge or verify a receipt through InfinitePay. It records the operator's confirmation and releases the purchased entitlement.

Work started on `main` at `218d5aa`. The last common source audit was `6e06634`; affected coupon, billing, package and contract paths were rechecked with `git log` and the working diff. Other sessions committed email, header and text-recovery work during this task, through `9253152`; those changes were preserved. This audit covers `9253152` plus the Gen2026 working changes committed with it, not an audit of every intervening feature.

The traced boundary is BMS session/`verifyAdmin` → translated Zod schema → server-derived actor/currency → `redeemManualCoupon` → one PostgreSQL transaction → existing package/cycle fulfillment → APP/SEQ readers. The new mode, product scope, request hash, unique receipt, SQL checks and result links are in the canonical schema and `20261007000000_manual_coupon_redemptions` migration. Gen2026 is provisioned without a Stripe object; an existing same-code coupon is preserved for explicit rollout review.

The transaction supports packages, finite B2B contracts and finite B2C subscriptions. Coupon/recipient locks serialize caps and grants; request replay returns the existing result, duplicate receipts and incompatible live subscriptions are rejected, and failure of the final audit write rolls back all benefits. The action then invokes existing first-payment partner provisioning; an invitation failure reports a successful settlement with a separate access follow-up. Manual B2C plans appear in the authenticated account's subscription grid and cannot start a concurrent Stripe subscription.

Feature contracts and operator runbooks are in [DISCOUNT-COUPONS](../../apps/bms/docs/DISCOUNT-COUPONS.md), [GENCODE-PACKAGES](../../apps/bms/docs/GENCODE-PACKAGES.md), [PARTNER-PLANS-CONTRACTS](../../apps/bms/docs/PARTNER-PLANS-CONTRACTS.md), [PARTNERS](../../apps/bms/docs/PARTNERS.md), [BILLING-QUOTAS](../../apps/app/docs/BILLING-QUOTAS.md), [PARTNER-PURCHASING](../../apps/seq/docs/PARTNER-PURCHASING.md) and [PARTNER-CREDITS](../PARTNER-CREDITS.md).

## Findings resolved during acceptance

The first custom B2C sale showed a correct active-period banner but its plan was absent from the FREE/PREMIUM-only offer grid. The account-specific query now includes the actually held manual plan, with a regression test and successful browser reload. The public offer query keeps its existing scope.

The first-payment partner path initially released credits without enabling the inactive OWNER. The BMS action now invokes existing access provisioning after settlement, with action tests and the before/after SEQ login above. A mail failure must not turn a committed financial result into a retryable failed sale.

The final coupon-list capture exposed a layout issue: the table's minimum width expanded the BMS content flex item and pushed the application button beyond the viewport. The content now has `min-w-0` and the coupon heading/action group wraps. The final build and browser capture below include these class changes.

Schema/lifecycle review found that a restrictive receipt-to-AppSale foreign key would block APP account deletion. The receipt now keeps a unique permanent `resultId` while its optional AppSale link uses `SetNull`. The final SQL check still enforces matching live result links. The new unit and real PostgreSQL regressions verify deletion, retained receipt/usage and idempotent retry. This preserves the existing account lifecycle and financial audit without modifying the account-deletion action or its mail behavior.

Parallel local sessions used the same hostname with different ephemeral secrets; a localhost cookie was invalidated by another session. Acceptance continued on the loopback IP with the correct app cookie. The new launcher host option aligns callbacks with that host; final normal-login verification is recorded below. The fixture initially lacked required tenant fields; it was corrected before successful seeded runtime use. Neither setup failure was treated as a feature pass.
