## Production migration procedure

The migration adds two tables and one nullable GenCode link. It is transactional.
The migration does not change existing customer, stock or sale rows.
The existing Vercel project uses protected Neon credentials.
The old local credential file is absent. Secret values cannot be pulled with the Vercel CLI.
The Chrome desktop integration is unavailable. The marketplace SSO link requires a browser session.
No secret was printed, reset or replaced.

[The release job](../../scripts/production-b2b-migration.mjs) runs only with an explicit APP production scope.
It checks the existing direct Neon host and requires exactly this pending migration.
It first reads all public tables in one repeatable-read transaction.
It stores exact JSON row text, column data, constraints, indexes, enums, sequence state and prior migration SQL.
It uploads the compressed snapshot to the existing private Blob store.
It reads the snapshot back and checks its SHA-256 checksum before migration.
This is a logical row snapshot. It is not a `pg_dump` file or a completed full recovery rehearsal.
Keep the snapshot and prior schema. A recovery operator must review the restore order and foreign keys.
Restore rows with PostgreSQL `json_populate_record` against the matching prior schema.
Never run an automatic restore against production.

The job then uses canonical `prisma migrate deploy` and checks the new empty tables and migration count.
It has no web route. It runs before the staged APP build.
The tracked APP Vercel build command runs it only with `B2B_MIGRATE=1`.
The release also sets `B2B_MIGRATION_PROJECT` to the verified APP project ID.
Do not use these flags again after the named migration is applied.
SEQ is built from the same reviewed source after the migration succeeds.
Promote the exact READY builds after readiness and access checks.
BMS uses the additive schema but has no changed product path in this release.
